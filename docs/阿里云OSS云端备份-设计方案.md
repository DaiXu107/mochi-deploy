# 阿里云 OSS 云端备份（RAM 子账号直传）— 设计方案

> 状态：待审阅 · 版本：v1.0
> 范围：以下仅为设计文档，**未改动任何代码**。审阅确认后再实现。

***

## 1. 目标

让每个用户用**自己的阿里云 OSS Bucket** 存储 mochi 的全量备份（聊天记录/字卡/头像/音乐/各类功能数据等），实现：

* **上传**：把当前全量数据包传到云端，实现跨设备备份。

* **恢复**：从云端拉取可靠的一份，走现有原子导入流程还原。

* **自动备份**（可选）：按开关定时/定期上传最新全量包。

**原则**：复用现有 [data-backup.js](../src/js/data-backup.js) 的"导出收集 / 导入恢复"逻辑，不另起数据读取。用户自带账号、各自隔离，互不影响。

***

## 2. 安全模型（为什么够安全）

* **RAM 子账号 + 最小权限**：每个用户自己在阿里云控制台创建 RAM 子账号，只授予"读写自己 Bucket 指定目录"的最小权限（见 §7 配置指引）。数据传到**他自己的 Bucket**。

* **密钥不进仓库/不进构建产物**：`AccessKeyId / AccessKeySecret` 只由用户在**运行时**填进设置页，仅存于本机 localStorage；源码与 GitHub 上不含任何密钥。

* **数据天然隔离**：A 用户看不到 B 用户的 Bucket；即便某用户密钥泄露，也仅影响他自己，不波及他人。

* **不用 STS / 不加后端**：本项目是纯前端 PWA（GitHub Pages），无服务器，不引入 STS 服务端签名，故采用 RAM 子账号直传。这是对"每个人自己管自己"场景的最简单可靠做法。

### 2.1 关于「代码在 GitHub 全公开 + 线上用 GitHub Pages」的安全性

**核心结论：安全的**——公开的只有代码，绝不包含任何用户名下的密钥。残余风险集中在"用户侧如何配置和使用 Key"，而非代码泄露。

| 关注点                    | 实际情况                                      | 属于哪方的风险      |
| ---------------------- | ----------------------------------------- | ------------ |
| 代码开源能否泄露密钥             | **不能**。AccessKey 只在用户运行时填进设置页，源码/产物/仓库零密钥 | 无            |
| 签名逻辑公开                 | OSS HMAC 签名本就是公开协议，浏览器端签名≠上传密钥            | 无            |
| 他人拿你源码做恶意版             | 无法访问任何人的数据（没有他们的 Key，数据在各用户自己的 Bucket）    | 低（通用 OSS 涉水） |
| 密钥出现在用户设备浏览器内存         | 单人自有设备可接受；**公共/共享设备不可接受**                 | 用户侧          |
| 用户误把**主账号/高权限 Key**填进来 | 一旦泄露，泄露面大（这是本方案唯一真正的安全命门）                 | 用户侧          |
| 密钥存本机 localStorage     | 设备被入侵/共享设备有被取风险                           | 用户侧          |

**对应设计约束（§7 强制写明）**：

1. **最小权限是硬性要求**：必须用独立 RAM 子账号，只授权"自己的 Bucket 指定前缀"，**绝不用主账号 Key**。
2. **设备安全提示**：只在可信/私人设备上填写密钥；泄露即到控制台作废并换新。
3. **可选更严格**：若某用户安全性要求高，可自行把子账号权限收窄到目录级、或定期轮换 Key；mochi 侧不做后端，不加 STS。

### 2.2 威胁建模：谁会发起攻击、能到什么程度

| 威胁者 / 场景     | 能否触达数据               | 破坏力             | mochi 侧对策               |
| ------------ | -------------------- | --------------- | ----------------------- |
| 攻击者拿到你的开源源码  | 无法（仓库里没有任何用户 Key）    | 无               | 源码/产物零密钥                |
| 获得某用户泄露的 Key | 能，但仅限该用户自己的 Bucket   | 取决于该用户配的权限      | §7 强制最小权限；泄露可到控制台作废     |
| 中间人窃听网络      | 基本不能（全程 HTTPS）       | 低               | GitHub Pages 天然 HTTPS   |
| OSS 端服务端静态明文 | 对象无加密时，离线拿到对象即可读     | 中               | **建议用户开 SSE 服务端加密（免费）** |
| 恶意钓鱼版 / 克隆站  | 高威胁：用户可能在假站填 Key 被套走 | 高（**开源最现实的威胁**） | 官方域名入口 + 提示核对地址；无法代码根治  |
| 设备被入侵 / 共享设备 | 若 Key 被读走则中招         | 高               | 只在可信设备填；泄露即作废换新         |

补充对策要点：

1. **开 SSE-OOS 服务端加密**（可选、免费）：Bucket 开启默认加密后，即使对象被越权/离线取走也读不出明文。这是"泄露后被读到"的最后一道闸，已写进 §7 配置步骤。
2. **防钓鱼是开源天然短板**：因为代码全公开，任何人都能 clone 出一个长得一模一样的页面做钓鱼版，骗用户在假站填 Key。代码层无法根除，只能在设置页/介绍页提示"请从官方入口进入、核对域名"，并明确**不要在任何第三方镜像填密钥**。
3. **localStorage 明文存 Key 的诚实边界**：浏览器端无法"真正加密"运行所需的密钥（运行时必须在内存可用），明文存本机是业界常态做法。真正的防线是"设备安全 + 最小权限"，而非客户端加密。

## 3. 实现方式：手写 OSS REST + HMAC 签名

### 3.1 为什么不用官方 `ali-oss` SDK

| <br />                 | 官方 SDK                                     | 手写 REST（本项目选用）                              |
| ---------------------- | ------------------------------------------ | ------------------------------------------- |
| 体积                     | 大，会撑爆 `SCRIPT_CHUNK_LIMIT` 拆块并加大包体         | 几百行自包含                                      |
| 与现有零依赖压缩构建兼容           | 需改造 [build.mjs](../build.mjs) 的逐行压缩器，维护成本高 | 完全兼容，加文件即可                                  |
| 离线 PWA / ServiceWorker | 外置依赖处理繁琐                                   | 内联进单文件，天然离线                                 |
| 能力                     | 断点续传/分片全                                   | 本场景仅需单对象上传/下载，够用                            |
| 断点续传                   | 需                                          | 聊天备份单文件大小受 OSS 单个对象上限（5GB）约束，个人场景远小于此，可不做分片 |

### 3.2 OSS PutObject / GetObject 签名（浏览器端）

OSS 的访问控制走 HTTP 请求头 `Authorization`，格式为：

```
Authorization: OSS <AccessKeyId>:<Signature>
```

`Signature = Base64( HMAC-SHA1(AccessKeySecret, StringToSign) )`

`StringToSign` 规范串（不启用 STS、不用 Content-MD5 时）：

```
<VERB>\n
\n                          // Content-MD5（空）
\n                          // Content-Type（空，或填 application/json）
<Date>\n                   // IMF-fixdate，如 new Date().toUTCString()
\n                          // CanonicalizedOSSHeaders（空，无需 x-oss-* 头）
<CanonicalizedResource>    // /<bucket>/<object> （含?子资源，本项目无）
```

浏览器端用 `crypto.subtle.importKey('raw', secret, {name:'HMAC', hash:'SHA-1'})` 后 `sign()`，再 `btoa` 得到签名。前提：**HTTPS 安全上下文**（GitHub Pages 天然满足）。

**要求用户配置 Bucket CORS**（§7 有步骤）：`AllowedOrigin` 配 `*`（或你的 GitHub Pages 域名）、`AllowedMethod` 配 `PUT/GET/HEAD`、`AllowedHeader` 配 `*`。否则浏览器跨域直传/下载会被拦。

### 3.3 关键常数与唯一端点

* Host：`<bucket>.<region-endpoint>`，如 `mybackup.oss-cn-hangzhou.aliyuncs.com`。

* 上传：`PUT https://<bucket>.<endpoint>/<object>`，body 为备份 JSON 文本。

* 下载：`GET https://<bucket>.<endpoint>/<object>`，得到备份 JSON 文本。

* 对象名（object key）：建议 `mochi-backup/<年-月-日__时-分-秒>.json`，按时间戳存多份。恢复时从云端列目录取最新一份（`GET ?prefix=mochi-backup/`）或由用户指定。**注意** **`ListObjects`** **返回的是 XML**：需解析 `<Key>`/`<LastModified>` 并按 `LastModified` 降序取最新（修复 §11#6）。

**传输实现约定（修复 §11#2/#3/#4）**：

* **上传/下载一律用** **`XMLHTTPRequest`**（配 `upload.onprogress` / `onprogress` 做进度条）。`fetch` 拿不到上传进度且 body 会再占一份内存，大备份下不适用。

* **只新增、不覆盖（版本化）**：对象名带时间戳，每次上传生成新对象，自动/手动都不删除旧版（`last` 只记录本次）。这样即使某次上传的是坏备份，云端仍有历史好份可回。

* **上传前健康 + 体积校验**：校验导出数据非空、含聊天记录等关键内容；估算体积，超过阈值（如 200MB）给出警告并提示"备份过大可能卡顿/失败"，由用户确认是否仍上传（修复 §11#2/#3）。

* **下载解析的内存峰值**：下载 JSON → `JSON.parse` → `doImportGo` 遍历，为大备份手机可能会卡，属可接受取舍，界面上大文件先预警。

## 4. 配置项与存储键

存 localStorage，全局键（不带 per-cid，云备份对整个应用）：

| 键                               | 含义                                            | 类型         |
| ------------------------------- | --------------------------------------------- | ---------- |
| `xy-home-v2:cloud-oss:enabled`  | 自动备份开关                                        | `"1"`/`""` |
| `xy-home-v2:cloud-oss:bucket`   | Bucket 名                                      | string     |
| `xy-home-v2:cloud-oss:endpoint` | 区域 Endpoint（如 `oss-cn-hangzhou.aliyuncs.com`） | string     |
| `xy-home-v2:cloud-oss:ak`       | AccessKeyId                                   | string     |
| `xy-home-v2:cloud-oss:sk`       | AccessKeySecret                               | string     |
| `xy-home-v2:cloud-oss:last`     | 最近一次成功上传的本地时间戳                                | number     |

**密钥存储提示**：`ak` / `sk` 仅存本机 localStorage。文档中要告知用户"请勿在公共/他人设备勾选记住、注意设备安全"。

**密钥防泄漏 + 体验闭环（修复 §11#1）**：

* `cloud-oss:ak` / `cloud-oss:sk` **必须从一切全量导出（本地下载、云上传）中排除**。在 `data-backup.js` 的导出 getter 上新增黑名单（同现有 `SNAPSHOT_KEY` 的排除机制），凡是 `xy-home-v2:cloud-oss:*` 一律不打包。

* 因此**云恢复后本机密钥为空**：恢复流程结束会自动跳回「云端备份」设置，提示用户重填 `ak / sk`（这是预期行为，不是丢数据）。设置页 upload 前若发现密钥为空，也提示先填写。

* 导出排除后，`exportToData` 产出的备份里不应出现任何 `cloud-oss:*` 键——作为哨兵自检项之一（见 §9）。

## 5. 数据流

### 5.1 上传（手动 / 自动）

**数据就绪门控（修复点③）**：导出必须先保证本地数据已就绪。应用启动时 `idbRestore`（`data-backup.js`）可能还没回填完成，此时读到的键为空，直接收集会导出**不完整/空包**并覆盖性上传。因此：

* **自动备份**必须在\*\*「数据就绪」信号之后**才允许收集上传——本项目以** **`mochi-restore-done`** 事件（或等价的就绪标志）为准；未就绪则延迟/跳过\*\*并在就绪后补跑，绝不带空数据上传。

* **手动上传**同理：点击时先校验就绪标志，未就绪提示"数据正在就绪，稍后再试"。

```
用户点「上传到云端」/ 自动备份触发
        │
        ▼
⓿ 数据就绪门控（修复点③）：等待 mochi-restore-done / 本地就绪标志；
   自动备份未就绪 → 延迟到就绪后补跑 / 跳过并提示；手动未就绪 → 提示稍后再试
        ▼
① 填写检查：ak/sk/bucket/endpoint 是否齐全；缺失 → 提示先去设置里填（修复 §11#1 体验闭环）
        │
        ▼
② 调用 window.exportToData()      ← 复用 data-backup.js 导出收集，已排除 cloud-oss:* 密钥
        │  返回备份 JSON 字符串
        ▼
③ 健康 + 体积校验：非空、含聊天等；超阈值预警让用户确认（修复 §11#2/#3）
        │
        ▼
④ XHR：PUT https://<bucket>.<endpoint>/mochi-backup/<时间戳>.json（版本化，只新增不覆盖）
        │  upload.onprogress → 进度条；手写 HMAC 签名
        ▼
成功 → 记录 last 时间戳 → 提示「已备份到云端，xx MB」
失败 → 分类提示（网络错 / 权限错 403 / CORS 被拦），不做半途中止、不删旧版
```

### 5.2 恢复（手动）

```
用户点「从云端恢复」
        │
        ▼
① XHR 列目录（解析 XML）→ 列出 mochi-backup/* + 各自时间；默认选最新一份
        ▼
② 时间比对（修复 §11#4）：云端最新一份若【早于】本地 last → 提示
   "云端备份早于你本机最近备份，恢复可能丢掉本地新数据"，用户确认后才继续
        ▼
③ 强确认 + 预览：二次确认文案 + backupSummary 预览所含数据；提示
   "恢复会覆盖当前数据，建议先『上传到云端』保存当前版本保底"
        │
        ▼
④ XHR 下载所选对象 → JSON.parse → 生成 {ls, idb} 数据对象
        ▼
⑤ 走现有 doImportGo(data)   ← 复用原子恢复 + idbRestore 回填
        ▼
⑥ 进度面板 → 刷新页面 → 自动跳回「云端备份」设置，提示重填 ak/sk（修复 §11#1）
```

### 5.3 与现有导出的共享

* 从 `doExport` 中抽取"收集→打包 JSON"部分为新公共函数 `window.exportToData()`（返回 JSON 字符串）。**下载到本机**仍走原 `doExport` 保存流程，**云端上传**复用同一份产物，保证两端数据完全一致、不缺项。

* `cloud-oss:*` 密钥的排除在 `exportToData` 里**统一切生效**——无论下载到本机还是上传云端，产物都不含密钥（修复 §11#1）。

* **内容级加密为可选增强（默认不做）**：SSE-OSS（§7）属于"防陌生人"；若某用户希望连服务商明文都不可见，需另加"密码派生密钥 + AES-GCM 加密备份体"。本方案**不内置**，需时再增强设计（见 §10）。

* 恢复端直接调用 `data-backup.js` 已存在的 `doImportGo`，原子性/回滚/IDB 兜底全部沿用，不重复实现。

## 7. 用户侧配置指引（需要写进设置页操作说明 / 介绍页）

1. 登录阿里云控制台 → 新建 **RAM 子账号**，仅授权目标 Bucket 指定前缀的最小权限（避免误授整个账号权限）。
2. 创建 **OSS Bucket**，记录 Bucket 名与区域 Endpoint。
3. 在该 Bucket 的「权限管理 → 跨域设置（CORS）」添加规则：

   * 来源：`*`

   * 方法：`PUT, GET, HEAD`

   * 允许 Headers：`*`

   * 暴露 Headers：`ETag`（可选）
4. （**强烈建议，免费**）在 Bucket「服务端加密」开启**默认加密（SSE-OSS）**——即使备份对象被越权/离线取走也读不出明文（详见 §2.2）。
5. 将子账号的 `AccessKeyId / AccessKeySecret` 填进 mochi 设置页「云端备份」。

> 安全提示（§2.1 对应设计约束）：仅在可信/私人设备填写，只在本机生效；如泄露，到 RAM 控制台作废该子账号并换新。**不要在任何第三方镜像/克隆站填写密钥**。

## 8. 关键风险与边界

* **依赖顺序**：`cloud-backup.js` 运行时才调用 `window.exportToData` / `doImportGo`，均在页面加载后可用，不受 build 顺序影响；但为清晰仍将其排在 `data-backup.js` 前。

* **`crypto.subtle`** **需 HTTPS**：GitHub Pages 已 HTTPS，OK；本地 `file://` 打开无法用 crypto.subtle，云端备份在 `file://` 下不可用（文档注明）。

* **CORS 未配置**：报错应明确提示"请检查 Bucket 跨域设置"，而非笼统"网络错误"。

* **超大单个对象**：OSS 单对象上限 5GB，聊天备份（含图片 base64）一般远小于此；暂不做分片，若未来超限再补。

* **文件：一定不能把 AccessKey 写进任何源码/产物**，构建后哨兵检查只验证代码特征，密钥在运行时才输入。

* **自动备份的触发**：建议低频（每次启动后/手动触发为主），避免频繁写 OSS 产生流量费用；默认关，用户开。**必须在本地数据就绪（`mochi-restore-done`）之后再触发**（修复点③）：启动瞬间 `idbRestore` 未回填时导出的包为空/半成品，不能覆盖云端正常备份；未就绪则延迟到就绪后补跑，并做健康校验（§5.1⓿）。自动备份失败时要提示"上次备份失败/从未备份"，避免用户误以为已上传。

***

## 9. 验收与回归防线（实现后执行）

* 新增 `FIX_SENTINELS` 哨兵：`cloud-backup.js` 的 `window.cloudOss` 或 HMAC 签名函数名特征。

* 手测路径：

  1. 配置 RAM 子账号 + CORS，点「上传到云端」→ 成功、对象名带时间戳。
  2. 清本地数据 → 「从云端恢复」→ 聊天/头像取回，核对条数。
  3. 未配 CORS / 密钥错 → 报错提示友好。
  4. 自动备份开关开 → 触发时上传，成功后 `last` 更新。
  5. `node build.mjs` 后看哨兵输出 + `npm run verify` 系列（无头 Chrome 布局）。
  6. **密钥不泄漏**：`node --check` 后，导出/上传产物 grep 不得含 `cloud-oss:ak/sk` 值；恢复后设置页自动引导重填密钥（修复 §11#1）。
  7. **坏数据不覆盖好备份**：模拟本地数据损坏触发自动上传，确认新对象产生、旧对象保留（版本化，修复 §11#2）。
  8. **恢复防误覆盖**：云端最新早于本机 `last` 时给出提示并需二次确认；展示 `backupSummary` 预览（修复 §11#4）。
  9. **上传进度**：大备份上传显示进度条（XHR `upload.onprogress`）；超阈值体积预警（修复 §11#3）。
  10. **自动备份就绪门控**（修复点③）：应用启动即触发自动备份开关，确认在 `idbRestore` 未回填时**不会上报空包**；就绪标志出现后才上传，且成功后才更新 `last`；未就绪/失败有明确提示。

## 10. 明确不做（本次范围外）

* 不做后端 / 不做 STS 服务端签名。

* 不做多人共享协作同步（仅个人单向备份/恢复）。

* 不做增量 diff，全量包覆盖式备份（与现有手动导出一致）。

* **默认不做内容级加密**（密码+AES-GCM 加密备份体）：SSE-OSS 已满足"防陌生人"；若未来有"连服务商明文都不可见"的需求，再按 §5.3 的可选项增强设计（会增加密钥派生/密钥遗忘处理复杂度）。
